## 1. Обозначения и контракт данных

### 1.1 Нотация псевдокода

```
:=            присваивание
=             равенство
Σ(x ∈ X) f(x) сумма по множеству
|X|           мощность множества
⌊x⌋           округление вниз
median(X)     медиана
mean(X)       среднее арифметическое
pstdev(X)     среднеквадратическое отклонение генеральной совокупности
[a, b]        отрезок, границы включаются
```

Все денежные величины — в рублях, с точностью до копейки. Все доли — безразмерные числа в отрезке [0, 1], если явно не сказано иное.

### 1.2 Транзакция

Единица обработки после нормализации. Одна проводка по счёту 51.

| Поле | Тип | Смысл | Обязательность |
|------|-----|-------|----------------|
| `row_no` | целое | номер строки в исходном файле; основа трассируемости | обязательно |
| `date` | дата | дата операции | обязательно |
| `doc_type` | строка | «Поступление на расчетный счет», «Списание с расчетного счета» | опционально |
| `doc_no` | строка | номер платёжного документа | опционально |
| `account_no` | строка | расчётный счёт клиента, по которому прошла операция | опционально |
| `bank_name` | строка | банк обслуживания счёта | опционально |
| `corr_account` | строка | корреспондирующий счёт с субсчётом, например `62.01` | опционально |
| `counterparty` | строка | контрагент из аналитики проводки | опционально |
| `contract` | строка | договор из аналитики проводки | опционально |
| `purpose` | строка | назначение платежа или содержание проводки | опционально |
| `inflow` | число | сумма по дебету счёта 51, поступление | обязательно |
| `outflow` | число | сумма по кредиту счёта 51, списание | обязательно |

| `category` | перечисление | категория, присваивается алгоритмом A3 | вычисляемое |

**Инвариант И-1.** Ровно одно из полей `inflow`, `outflow` строго положительно, второе равно нулю. Операция без суммы отбраковывается на этапе A1.

**Инвариант И-2.** `row_no` уникален в пределах анализа и указывает на первую строку блока операции в исходном файле.

**Инвариант И-3.** Значения `category` присваиваются ровно один раз алгоритмом A3 и могут быть изменены только алгоритмом A4 и только на `TRANSIT_SUSPECT` или `INTERNAL_TRANSFER`.

Альтернативная трактовка — считать их выводом собственнику по аналогии с дивидендами — даёт более высокий свободный поток и более высокий лимит.

## 2. Алгоритм A1. Чтение печатной формы 1С

**Вход:** файл `.xlsx` или `.xls`.
**Выход:** упорядоченный список транзакций и метаданные карточки.
**Сложность:** O(R × C), где R — число строк, C — число колонок.

### 2.1 Почему это не разбор таблицы

Выгрузка «Карточка счёта» — печатная форма отчёта, а не выгрузка данных. Отсюда все меры ниже. Восемь свойств, которые обязан переживать ридер, наблюдаются в реальных выгрузках и воспроизведены в генераторе синтетики.

| Код | Свойство выгрузки | Мера |
|-----|-------------------|------|
| P1 | шапка не в первой строке: выше организация, ИНН, название отчёта, период | автопоиск строки заголовка |
| P2 | одна операция занимает 2–4 строки: дата и документ, контрагент, договор, назначение | группировка строк в блок |
| P3 | объединённые ячейки | разворачивание диапазонов до чтения |
| P4 | суммы текстом с неразрывным пробелом и десятичной запятой | нормализация числа |
| P5 | даты строками в разных форматах | мультиформатный разбор |
| P6 | строки сальдо и оборотов вперемешку с проводками | отбраковка с сохранением значений |
| P7 | несколько расчётных счетов в одной карточке, разделённые строкой субконто | отслеживание текущего счёта |
| P8 | корсчёт с субсчётом | хранение полностью, разбор по префиксу |

### 2.2 Шаг 1. Загрузка сетки с разворачиванием объединений

Библиотеки чтения возвращают значение объединённого диапазона только в левой верхней ячейке, остальные — пустые. Если этого не исправить, колонки «съедут».

```
ФУНКЦИЯ load_grid(file) -> матрица строк
    grid := прочитать все ячейки листа 1 как текст
    ДЛЯ каждого объединённого диапазона (r1..r2, c1..c2):
        v := grid[r1][c1]
        ЕСЛИ v непусто:
            ДЛЯ r ОТ r1 ДО r2, ДЛЯ c ОТ c1 ДО c2: grid[r][c] := v
    ВЕРНУТЬ grid
```

### 2.3 Шаг 2. Автопоиск шапки

```
КЛЮЧИ := {"период", "документ", "дебет", "кредит", "сальдо", "аналитика"}

ФУНКЦИЯ find_header(grid) -> индекс строки
    ДЛЯ i ОТ 0 ДО min(40, |grid|):
        text := нормализовать(соединить(grid[i], " "))
        ЕСЛИ |{k ∈ КЛЮЧИ : k ⊂ text}| ≥ 3: ВЕРНУТЬ i
    ОШИБКА "не найдена строка заголовка карточки счёта"
```

Нормализация текста: приведение к нижнему регистру, замена «ё» на «е», схлопывание пробельных последовательностей в один пробел, удаление неразрывных пробелов.

### 2.4 Шаг 3. Разбор двухуровневого заголовка

Заголовок 1С двухуровневый: «Дебет» объединён над подколонками «Счет» и «Сумма». После разворачивания объединений обе подколонки в верхней строке содержат «Дебет».

```
ФУНКЦИЯ build_column_map(grid, h) -> отображение имя -> индекс колонки
    ДЛЯ c ОТ 0 ДО ширина:
        t := нормализовать(grid[h][c] + " " + grid[h+1][c])
        ЕСЛИ "период" ⊂ t ИЛИ t = "дата":            date := c
        ИНАЧЕ ЕСЛИ "документ" ⊂ t:                    doc := c
        ИНАЧЕ ЕСЛИ "аналитика дт" ⊂ t:                analytics_dt := c
        ИНАЧЕ ЕСЛИ "аналитика кт" ⊂ t:                analytics_kt := c
        ИНАЧЕ ЕСЛИ "дебет" ⊂ t И ("счет" ⊂ t ИЛИ "кор" ⊂ t):  debit_acc := c
        ИНАЧЕ ЕСЛИ "дебет" ⊂ t:                       debit_amt := c
        ИНАЧЕ ЕСЛИ "кредит" ⊂ t И ("счет" ⊂ t ИЛИ "кор" ⊂ t): credit_acc := c
        ИНАЧЕ ЕСЛИ "кредит" ⊂ t:                      credit_amt := c
        ИНАЧЕ ЕСЛИ "сальдо" ⊂ t:                      balance := c
        ИНАЧЕ ЕСЛИ "назначение" ⊂ t:                  purpose := c
    ЕСЛИ {date, debit_amt, credit_amt} ⊄ найденные: ОШИБКА
```

Порядок проверок значим: условие с «счет» обязано проверяться раньше общего условия, иначе колонка счёта будет принята за колонку суммы.

### 2.5 Шаг 4. Нормализация чисел и дат

```
ФУНКЦИЯ parse_amount(raw) -> число
    ЕСЛИ raw число: ВЕРНУТЬ raw
    t := удалить из raw все символы кроме цифр, запятой, точки, минуса
    ЕСЛИ в t есть И запятая И точка:  t := удалить точки, запятую -> точка
    ИНАЧЕ:                             t := запятую -> точка
    ВЕРНУТЬ округлить(число(t), 2)  ИЛИ 0 при неудаче
```

Форматы дат, принимаемые последовательно: `ДД.ММ.ГГГГ ЧЧ:ММ:СС`, `ДД.ММ.ГГГГ ЧЧ:ММ`, `ДД.ММ.ГГГГ`, `ГГГГ-ММ-ДД ЧЧ:ММ:СС`, `ГГГГ-ММ-ДД`, `ДД/ММ/ГГГГ`. При неудаче — попытка выделить подстроку вида `ДД.ММ.ГГГГ` в начале значения.

### 2.6 Шаг 5. Проход по строкам и сборка блоков

```
ФУНКЦИЯ read_card(file) -> (транзакции, метаданные)
    grid := load_grid(file);  h := find_header(grid);  cols := build_column_map(grid, h)
    meta := разобрать преамбулу grid[0..h): организация, ИНН, границы периода
    account := НЕТ;  block := []

    ДЛЯ i ОТ h+1 ДО |grid|:
        row := grid[i]
        ЕСЛИ row пустая: ПРОДОЛЖИТЬ
        ЕСЛИ нормализовать(row[cols.date]) ∈ {"период", "дата"}: ПРОДОЛЖИТЬ   // вторая строка шапки

        marker := начинается ли соединение первых четырёх ячеек с одного из
                  {"сальдо на начало", "сальдо на конец", "обороты за период",
                   "оборот за период", "итого"}
        ЕСЛИ marker ≠ НЕТ:
            flush(block);  absorb_totals(meta, row, marker);  ПРОДОЛЖИТЬ

        ЕСЛИ в первых трёх ячейках найден 20-значный номер счёта
             И суммы дебета и кредита пусты:
            flush(block);  account := найденный номер;  bank := остаток строки;  ПРОДОЛЖИТЬ

        d := parse_date(row[cols.date])
        ЕСЛИ d ≠ НЕТ:  flush(block);  block := [row];  block_row_no := i+1
        ИНАЧЕ ЕСЛИ block ≠ []: block += row
        ИНАЧЕ: счётчик нераспознанных дат += 1

    flush(block)
    отсортировать транзакции по (date, row_no)
```

Функция `flush` собирает накопленный блок в одну транзакцию, `absorb_totals` сохраняет заявленные в файле сальдо и обороты — они понадобятся алгоритму A2.

### 2.7 Шаг 6. Сборка транзакции из блока

Ключевая деталь: для счёта 51 контрагент находится в аналитике **противоположной** стороны проводки.

```
ФУНКЦИЯ build_transaction(block, cols, account) -> транзакция
    head := block[0]
    inflow := parse_amount(head[cols.debit_amt]);  outflow := parse_amount(head[cols.credit_amt])
    ЕСЛИ inflow = 0 И outflow = 0: искать суммы в остальных строках блока
    ЕСЛИ обе всё ещё 0: ВЕРНУТЬ НЕТ                       // не проводка

    is_inflow := inflow > 0
    debit_acc  := первая непустая строка колонки debit_acc в блоке
    credit_acc := первая непустая строка колонки credit_acc в блоке

    // поступление проводится Дт 51 Кт X, списание Дт X Кт 51
    corr := ЕСЛИ is_inflow ТО credit_acc ИНАЧЕ debit_acc
    ЕСЛИ corr начинается с "51": corr := ЕСЛИ is_inflow ТО debit_acc ИНАЧЕ credit_acc

    analytics_corr := ЕСЛИ is_inflow ТО собрать(cols.analytics_kt) ИНАЧЕ собрать(cols.analytics_dt)
    lines := непустые строки analytics_corr
    counterparty := lines[0]
    contract     := первая из lines[1..], начинающаяся с "договор"
    purpose      := соединить остальные строки lines[1..] и колонку purpose
```

Функция «собрать» склеивает значения колонки по всем строкам блока, дополнительно разбивая многострочные ячейки по переносам строк и отбрасывая дубликаты. Это покрывает оба варианта выгрузки: и когда аналитика разложена по строкам, и когда она лежит одной ячейкой с переносами.

## 3. Алгоритм A2. Контроль целостности карточки

**Вход:** транзакции и метаданные.
**Выход:** список проверок с признаком «критическая» и итоговый признак пригодности.

Смысл: не считать лимит по недостоверному файлу. Клиент может подать карточку за неполный период, из другой базы или с обрезанными строками. Все три случая ловятся арифметикой самого файла.

| Код | Проверка | Формула или условие | Критическая | Порог |
|-----|----------|---------------------|-------------|-------|
| V1 | Сходимость сальдо | \|(B₀ + Σinflow − Σoutflow) − B₁\| ≤ ε | да | ε = 1 ₽ |
| V2 | Совпадение с итогами файла | \|Σinflow − D\| ≤ ε и \|Σoutflow − K\| ≤ ε | да | ε = 1 ₽ |
| V3 | Глубина периода | число календарных месяцев ≥ 6 | да | 6 мес |
| V4 | Непрерывность операций | max разрыв между соседними датами ≤ 21 дн | нет | 21 дн |
| V5 | Распознавание дат | доля строк с нераспознанной датой ≤ 1 % | да | 1 % |
| V6 | Полнота реквизитов | доля суммы операций без корсчёта и без назначения ≤ 5 % | нет | 5 % |
| V7 | Отсутствие валютных операций | нет операций с корсчётом, начинающимся на 52 | нет | — |
| V8 | Отсутствие дублей | нет полных совпадений (дата, суммы, контрагент, назначение) | нет | — |

Где B₀ и B₁ — сальдо на начало и конец из файла, D и K — заявленные в файле обороты по дебету и кредиту.

**Замечание по V1.** Печатная форма не сохраняет знак сальдо. Сравнение выполняется как минимум из модуля разности и разности модулей: `Δ := min(|E − B₁|, ||E| − |B₁||)`, где E — расчётное конечное сальдо.

**Замечание по V3.** Число месяцев считается как `(год₂ − год₁) × 12 + (месяц₂ − месяц₁) + 1`, то есть по календарным месяцам, а не по дням.

Провал любой критической проверки означает: расчёт лимита не выполняется, выдаётся отчёт о качестве данных, решение — отказ с указанием кода проверки.

## 4. Алгоритм A3. Классификация операций

**Вход:** транзакция, ИНН клиента.
**Выход:** категория и источник решения.
**Сложность:** O(N × P), где P — число правил; на практике доминирует стоимость регулярных выражений.

### 4.1 Двухуровневая логика и порядок разрешения

Корреспондирующий счёт — это уже выполненная бухгалтером клиента экономическая квалификация платежа. Именно он даёт основную точность; словарь назначений уточняет там, где счёт неоднозначен.

```
ФУНКЦИЯ classify(tx, client_inn) -> (категория, источник)
    text := нормализовать(counterparty + " " + contract + " " + purpose + " " + doc_type)
    by_account := account_category(tx.corr_account, tx.is_inflow)
    pattern    := правило с максимальным приоритетом среди сработавших на text
                  и подходящих по направлению

    ЕСЛИ pattern ≠ НЕТ И pattern.priority ≥ 85:
        категория := pattern.category;      источник := "pattern:" + pattern.name
    ИНАЧЕ ЕСЛИ by_account ≠ НЕТ:
        категория := by_account;            источник := "corr_account:" + corr_account
    ИНАЧЕ ЕСЛИ pattern ≠ НЕТ:
        категория := pattern.category;      источник := "pattern:" + pattern.name
    ИНАЧЕ:
        категория := UNCLASSIFIED

    ЕСЛИ client_inn ≠ НЕТ И client_inn ⊂ counterparty:
        категория := INTERNAL_TRANSFER;     источник := "own_inn"
```

**Порог перекрытия 85** разделяет правила на два класса. Правила с приоритетом не ниже 85 перекрывают вывод по корсчёту — они нужны там, где через один счёт проходят экономически разные операции (счёт 76) либо где требуется детализация внутри операционного оттока (аренда и связь проводятся по счёту 60, но нужны отдельно для индикатора T6). ### 4.4 Две ловушки, стоящие отдельного предупреждения

**Ловушка НДС.** Оборот «в т.ч. НДС 20 %» присутствует в назначении почти каждого коммерческого платежа. Правило, реагирующее на подстроку «НДС» или на слово «налог», отправляет в категорию налогов **все** расчёты с поставщиками, и налоговая нагрузка компании начинает выглядеть как 60 % оборота. Поэтому правило `tax_keywords` опирается на устойчивые обороты («единый налоговый платеж», «налог на прибыль»), а не на отдельные слова, а основную работу выполняет правило `tax_authority` по получателю платежа.

**Ловушка казначейства.** Правило по получателю «УФК» имеет высокий приоритет и без специальных мер поглощает страховые взносы и НДФЛ, которые тоже уходят в казначейство. В результате в системе не остаётся ни одной операции категории `OPEX_PAYROLL_TAX`, и индикатор реальности фонда оплаты труда становится красным у всех клиентов подряд. Поэтому правила `payroll_ndfl` и `social_contrib` имеют приоритет 97 — выше, чем `tax_authority` с приоритетом 95.

Обе ошибки были допущены и обнаружены на синтетических данных при разработке прототипа. Рекомендуется закрепить их регрессионными тестами до начала калибровки.

### 4.5 Метрика полноты классификации

```
auto_classified_share := Σ(tx : category ≠ UNCLASSIFIED) amount / Σ(all tx) amount
```

Целевое значение — не ниже 0,95. Если доля неклассифицированного превышает 15 % оборота, заявка уходит на ручной разбор независимо от прочих факторов.

## 5. Алгоритм A4. Парное сопоставление

**Вход:** классифицированные транзакции.
**Выход:** проставленные `link_id` и `excluded_reason`, изменённые категории для транзита.

Модуль решает три задачи: снять двойной счёт, отделить транзит и сохранить трассируемость — каждая пара получает общий идентификатор, по которому в отчёте раскрываются обе стороны.

### 5.1 Внутренние переводы между собственными счетами

```
ФУНКЦИЯ link_internal_transfers(txs) -> число пар
    outs := {tx : category = INTERNAL_TRANSFER И outflow > 0}
    ins  := {tx : category = INTERNAL_TRANSFER И inflow  > 0}
    ДЛЯ каждого o ∈ outs:
        найти первый неиспользованный i ∈ ins такой, что
            |i.date − o.date| ≤ 1 день  И  |i.inflow − o.outflow| < 0,01 ₽
        ЕСЛИ найден: пометить оба excluded_reason := "internal_transfer", общий link_id
```

Обе стороны исключаются из оборота: иначе один и тот же рубль считается выручкой дважды.

### 5.2 Дубли эквайринга

```
ФУНКЦИЯ link_acquiring_duplicates(txs) -> число дублей
    ДЛЯ каждого a ∈ {tx : category = ACQUIRING_IN}:
        найти первый неиспользованный r ∈ {tx : category = REVENUE_OPERATING И inflow > 0}
            такой, что r.date = a.date И |r.inflow − a.inflow| < 0,01 ₽
        ЕСЛИ найден: r.excluded_reason := "acquiring_duplicate"
```

Поступления эквайринга — реальная розничная выручка и включаются в расчёт. Исключается вторая сторона дубля, если та же сумма проведена и через счёт 57, и через счёт 62.

### 5.3 Детектор транзита

Ключевое проектное решение: сопоставление строгое — только один к одному либо один ко многим на **одного и того же** контрагента. Схлопывание произвольных подмножеств платежей находит совпадение почти всегда и превращает детектор в генератор ложных срабатываний.

```
КОНСТАНТЫ: W := 3 дня, LO := 0,95, HI := 1,05

ФУНКЦИЯ detect_transit(txs) -> (число пар, объём транзита)
    inflows  := {tx : inflow > 0, excluded_reason = НЕТ,
                 category ∈ {REVENUE_OPERATING, OTHER_INCOME, UNCLASSIFIED}}
    outflows := {tx : outflow > 0, excluded_reason = НЕТ,
                 category ∉ НЕТРАНЗИТНЫЕ}
    used := ∅;  pairs := 0;  volume := 0

    ДЛЯ каждого inc ∈ inflows в порядке возрастания даты:
        cand := {o ∈ outflows : o ∉ used И inc.date ≤ o.date ≤ inc.date + W}
        best := НЕТ;  best_gap := ∞

        // вариант «один к одному»
        ДЛЯ каждого o ∈ cand:
            ratio := o.outflow / inc.inflow
            ЕСЛИ LO ≤ ratio ≤ HI И |ratio − 1| < best_gap:
                best := {o};  best_gap := |ratio − 1|

        // вариант «один ко многим на одного контрагента»
        ЕСЛИ best = НЕТ:
            ДЛЯ каждой группы g ⊂ cand с одинаковым контрагентом, |g| ≥ 2:
                ratio := Σ(o ∈ g) o.outflow / inc.inflow
                ЕСЛИ LO ≤ ratio ≤ HI И |ratio − 1| < best_gap:
                    best := g;  best_gap := |ratio − 1|

        ЕСЛИ best ≠ НЕТ:
            pairs += 1;  volume += inc.inflow
            inc.category := TRANSIT_SUSPECT;  inc.excluded_reason := "transit"
            все элементы best: excluded_reason := "transit", общий link_id, добавить в used
```

Множество НЕТРАНЗИТНЫЕ — категории, которые не могут быть транзитом по своей природе: заработная плата, взносы и НДФЛ, налоги, аренда, связь, комиссии банка, страхование, таможня, лизинг, погашение кредитов и процентов, принудительное взыскание, внутренние переводы, возвраты покупателям, капитальные вложения.

**Расчёты с поставщиками в это множество намеренно не входят.** Транзит всегда маскируется именно под оплату поставщикам, и отсечение категории обнулило бы детектор.

**Калибровка полосы допуска.** На синтетическом наборе полоса 0,90–1,10 давала 11 % ложной транзитности на здоровой оптовой торговле, полоса 0,95–1,05 — около 8 % при неизменной детекции реальной схемы (81 %). Дальнейшее сужение до 0,97–1,03 снижает шум до 5 %, но теряет схемы с комиссией посредника выше 3 %. Полоса подлежит перекалибровке на вашей выборке.

**Транзит требует двух реакций одновременно.** Его нельзя просто вычесть и посчитать лимит от остатка: компания, у которой 60 % притока транзитные, — это не клиент с меньшим лимитом, а клиент с другим риск-профилем. Поэтому транзит и вычитается из расчётной базы, и поднимает индикатор T3, который выше порога превращается в стоп-фактор S1.

## 6. Алгоритм A5. Очистка денежного потока

**Вход:** транзакции после A3 и A4.
**Выход:** агрегаты за период и помесячный ряд.

### 6.1 Мост от валового притока к свободному потоку

```
ВАЛОВОЙ ПРИТОК          := Σ(all tx) inflow
ВАЛОВОЙ ОТТОК           := Σ(all tx) outflow

ИСКЛЮЧАЕМЫЙ ПРИТОК      := Σ(tx : inflow > 0 И (excluded_reason ≠ НЕТ
                                                ИЛИ category ∈ НЕВЫРУЧКА)) inflow

КВАЛИФИЦИРОВАННЫЙ ПРИТОК := ВАЛОВОЙ ПРИТОК − ИСКЛЮЧАЕМЫЙ ПРИТОК
ОЧИЩЕННАЯ ВЫРУЧКА        := КВАЛИФИЦИРОВАННЫЙ ПРИТОК − Σ(category = REVENUE_RETURN) outflow

ОПЕРАЦИОННЫЙ ОТТОК       := Σ(tx : category ∈ ОПЕРАЦИОННЫЕ И excluded_reason = НЕТ) outflow
СВОБОДНЫЙ ПОТОК          := ОЧИЩЕННАЯ ВЫРУЧКА − ОПЕРАЦИОННЫЙ ОТТОК
```

Множество НЕВЫРУЧКА: `INTERNAL_TRANSFER`, `FIN_LOAN_IN`, `OWNER_CONTRIBUTION`, `DEPOSIT_IN`, `SUPPLIER_REFUND`, `LOAN_REPAY_IN`, `CASH_DEPOSIT`, `TRANSIT_SUSPECT`.

Множество ОПЕРАЦИОННЫЕ: `OPEX_SUPPLIERS`, `OPEX_PAYROLL`, `OPEX_PAYROLL_TAX`, `OPEX_TAXES`, `OPEX_RENT`, `OPEX_COMMS`, `OPEX_BANK_FEES`, `INSURANCE`, `CUSTOMS`, `LEASING`, `FACTORING`, `CASH_WITHDRAWAL`, `CASH_PROXY`.

**Инвариант И-4, обязательный к проверке автотестом.**

```
ВАЛОВОЙ ПРИТОК − Σ(по всем группам исключений) сумма = КВАЛИФИЦИРОВАННЫЙ ПРИТОК   (до копейки)
```

### 6.2 Помесячный ряд

Все три величины считаются также помесячно: месяц операции определяется как год и месяц её даты. Помесячный ряд — основа для оценки волатильности, тренда, худшего месяца и медианы свободного потока, поэтому считать только агрегат за период недостаточно.

Для каждого месяца m:

```
adjusted_revenue[m]  := Σ(tx ∈ m : inflow > 0, не исключён) inflow
                        − Σ(tx ∈ m : category = REVENUE_RETURN) outflow
operating_outflow[m] := Σ(tx ∈ m : category ∈ ОПЕРАЦИОННЫЕ, не исключён) outflow
fcf[m]               := adjusted_revenue[m] − operating_outflow[m]
```

### 6.3 Группировка исключений для отчёта

Исключения группируются по причине: `internal_transfer`, `acquiring_duplicate`, `transit`, а для остального — по категории. Каждая группа хранит сумму, долю валового притока и **список номеров строк исходного файла**. Это требование трассируемости: любая цифра отчёта обязана раскрываться до конкретных операций.

## 7. Алгоритм A6. Индикаторы риска

**Вход:** транзакции, помесячный ряд, агрегаты.
**Выход:** пятнадцать индикаторов со значением, статусом и списком строк-источников.

### 7.1 Функция статуса

Каждый индикатор имеет пару порогов (amber, red) и направление.

```
ФУНКЦИЯ grade(v, amber, red, higher_is_worse) -> статус
    ЕСЛИ v = НЕТ: ВЕРНУТЬ NA
    ЕСЛИ higher_is_worse:
        ЕСЛИ v > red: RED;  ИНАЧЕ ЕСЛИ v > amber: AMBER;  ИНАЧЕ GREEN
    ИНАЧЕ:
        ЕСЛИ v < red: RED;  ИНАЧЕ ЕСЛИ v < amber: AMBER;  ИНАЧЕ GREEN
```

При нулевом знаменателе индикатор возвращает NA и не участвует в понижающем множителе лимита.

### 7.2 Ряд остатков по дням

Требуется индикаторам T5 и T14.

```
ФУНКЦИЯ daily_balances(txs) -> отображение дата -> остаток
    by_day := для каждой даты берём |balance_after| последней операции этого дня
    протянуть значения вперёд на все календарные дни между первой и последней датой
```

### 7.3 Определения индикаторов

Обозначения: `GI` — валовой приток, `GO` — валовой отток, `R` — очищенная выручка за период, `FCF` — свободный поток за период, `M` — число месяцев, `rev[m]` — помесячная очищенная выручка.

| Код | Название | Формула | Направление | Amber | Red | Источник логики |
|-----|----------|---------|-------------|-------|-----|-----------------|
| T1 | Налоговая нагрузка | (Σ`OPEX_TAXES` + Σ`OPEX_PAYROLL_TAX`) / GO | ниже хуже | 0,020 | 0,009 | 18-МР |
| T2 | Реальность ФОТ | \|{m : есть `OPEX_PAYROLL` и `OPEX_PAYROLL_TAX`}\| / M | ниже хуже | 0,80 | 0,50 | 18-МР |
| T3 | Транзитность | Σ(`TRANSIT_SUSPECT`) inflow / GI | выше хуже | 0,15 | 0,40 | 18-МР, 236-Т |
| T4 | Снятие наличных и подотчёт | (Σ`CASH_WITHDRAWAL` + Σ`CASH_PROXY`) / GO | выше хуже | 0,10 | 0,30 | 18-МР |
| T5 | Накопление остатка | mean(daily_balances) / (GI / M) | ниже хуже | 0,05 | 0,02 | 18-МР |
| T6 | Признаки хоздеятельности | \|{m : есть аренда, связь или комиссии}\| | ниже хуже | 6 мес | 3 мес | 18-МР |
| T7 | Концентрация покупателей | max доля контрагента в Σ`REVENUE_OPERATING` | выше хуже | 0,40 | 0,60 | практика |
| T8 | Волатильность выручки | pstdev(rev) / mean(rev) | выше хуже | 0,35 | 0,60 | практика |
| T9 | Тренд выручки | mean(rev[−3:]) / mean(rev[−6:−3]) − 1 | ниже хуже | −0,15 | −0,30 | практика |
| T10 | Долговая нагрузка | (Σ`FIN_LOAN_OUT` + Σ`FIN_INTEREST`) / R | выше хуже | 0,15 | 0,25 | практика |

| T14 | Дни без ликвидности | доля дней d, для которых balance[d] < ОПЕРАЦИОННЫЙ ОТТОК / число дней периода | выше хуже | 0,10 | 0,25 | практика |
| T15 | Качество разметки | Σ(`UNCLASSIFIED`) amount / (GI + GO) | выше хуже | 0,05 | 0,15 | внутреннее |

### 7.4 Уточнения, важные для воспроизведения

**T1.** Знаменатель — оборот по **списанию**. Формулировка 18-МР говорит о дебетовом обороте по счёту клиента в банковской терминологии, что соответствует кредиту счёта 51 в терминологии бухгалтерского учёта. Ошибка в выборе знаменателя меняет индикатор в разы.

**T2.** Если среднемесячная очищенная выручка ниже 5 млн ₽, красный статус смягчается до жёлтого: у микробизнеса без наёмных сотрудников отсутствие фонда оплаты труда является нормой, а не признаком технической компании.

**T5.** Знаменатель — **валовой**, а не квалифицированный приток. Логика 18-МР сравнивает остаток именно с общим объёмом движения по счёту. При использовании квалифицированного притока транзитная компания с малой очищенной выручкой выглядит как накапливающая деньги.

**T7.** Эквайринговые поступления исключены из расчёта концентрации: за расчётами банка-эквайера стоят тысячи розничных покупателей, что является противоположностью концентрации. Без этого исключения розничная сеть с долей эквайринга 72 % получает ложный красный флаг.

**T9.** Требует не менее шести месяцев истории, иначе возвращает NA.

**T14.** Порог ликвидности определён как средний дневной операционный отток: доля дней, когда остатка не хватало на один средний день операционных платежей.

## 8. Алгоритм A7. Расчёт лимита и решение

### 8.1 Принцип

Лимит — минимум из четырёх независимых ограничителей. Единой формулы нет намеренно: она даёт правдоподобное число, которое нечем защищать перед андеррайтером. Каждый ограничитель отвечает на свой вопрос, и в отчёте указывается, какой именно оказался связывающим.

### 8.2 Ограничитель L1. Масштаб выручки

Сколько банк готов дать бизнесу такого размера.

```
ARM := mean(rev[последние 6 месяцев])
L1  := k_отрасль × ARM
```

| Отрасль | k | Длительность цикла, дней |
|---------|---|--------------------------|
| Оптовая торговля и дистрибуция | 1,5 | 60 |
| Розничная торговля | 1,0 | 30 |
| Услуги | 1,2 | 45 |
| Производство | 1,5 | 75 |
| Строительство | 0,8 | 90 |
| Транспорт и логистика | 1,0 | 45 |

Коэффициент применяется к **месячной** выручке: значение 1,0 означает лимит, равный одному месячному обороту.

### 8.3 Ограничитель L2. Способность обслуживать долг

Сколько бизнес способен обслуживать.

```
FCF_med      := median(fcf[все месяцы])
max_payment  := max(FCF_med / DSCR_target, 0)
PV(r, n)     := (1 − (1 + r/12)^(−n)) / (r/12)
L2           := max_payment × PV(annual_rate, term_months)
```

При значениях по умолчанию `DSCR_target = 1,4`, `annual_rate = 0,24`, `term_months = 24`:

```
PV(0,24, 24) = (1 − 1,02^(−24)) / 0,02 = 18,9139
```

Медиана, а не среднее: она устойчива к единичным выбросам, характерным для сезонных бизнесов.

### 8.4 Ограничитель L3. Потребность в оборотном капитале

Сколько бизнесу реально нужно. Лимит выше потребности — это уже не оборотное финансирование, а источник вывода средств, и он ухудшает возвратность при формально хорошей марже.

```
daily_out := ОПЕРАЦИОННЫЙ ОТТОК / (число календарных дней периода)
L3        := daily_out × цикл_отрасли_в_днях
```

### 8.5 Ограничитель L4. Потолок продукта

```
L4 := 20 000 000 ₽      // беззалоговый транш сегмента, задаётся кредитной политикой
```

### 8.6 Сборка лимита

```
constraints  := {L1, L2, L3, L4}
binding      := argmin(constraints)
base         := min(constraints)

multiplier   := Π(по всем индикаторам)  1,00 если GREEN или NA
                                        0,90 если AMBER
                                        0,70 если RED
multiplier   := max(multiplier, 0,40)

final        := ⌊base × multiplier / 100 000⌋ × 100 000
range_low    := ⌊final × 0,8 / 100 000⌋ × 100 000
```

Итог выдаётся диапазоном `[range_low, final]`, а не точкой.

### 8.7 Стоп-факторы

При срабатывании любого — лимит равен нулю, решение «отказ».

| Код | Условие |
|-----|---------|
| S1 | T3 > 0,60 |
| S2 | T1 < 0,003 при валовом оттоке > 10 000 000 ₽ |
| S3 | T11 > 0,05 |
| S4 | число месяцев с отрицательным свободным потоком среди последних 6 ≥ 4 |
| S5 | mean(rev[последние 3 месяца]) < 300 000 ₽ |
| S6 | не пройдена хотя бы одна критическая проверка целостности (V1, V2, V3, V5) |
| S7 | T9 < −0,50 |

### 8.8 Решение

```
ЕСЛИ множество стоп-факторов не пусто:                    DECLINE
ИНАЧЕ ЕСЛИ есть хотя бы один индикатор со статусом RED:   MANUAL_REVIEW
ИНАЧЕ:                                                     AUTO_APPROVE
```

Дополнительно в `MANUAL_REVIEW` отправляются заявки, где доля неклассифицированного превышает 15 % оборота (индикатор T15 в красной зоне).

## 11. Воспроизведение во внутрибанковском контуре

### 11.1 Рекомендуемая последовательность работ

1. **Собрать выборку карточек.** 100–200 файлов из закрытых заявок с известным исходом. Без этого калибровка невозможна, а без калибровки модель остаётся экспертной.
2. **Реализовать A1 и A2, остановиться, измерить.** Доля файлов, прошедших контроль целостности, — первая честная метрика применимости подхода в вашем потоке.
3. **Перенести справочник корсчетов как есть.** Он отраслевой, а не банковский, и переносится без изменений.
4. **Реализовать A3, измерить долю неклассифицированного, донастроить словарь.** Это основная работа аналитика.
5. **Реализовать A4–A5 и сверить с разделом 9.** До этого момента расчёт лимита можно не трогать.
6. **Реализовать A6–A7 с вашими значениями коэффициентов.** Формулы переносятся, значения задаёт кредитная политика.
7. **Сделать отчёт для андеррайтера с трассируемостью.** Без него модель не примут в эксплуатацию: андеррайтер обязан видеть, из каких операций получилась каждая цифра.
8. **Провести ретроспективный прогон** на выборке из пункта 1 и сравнить решения модели с фактическими исходами.

### 11.2 Версионирование и журнал решений

Каждое решение обязано фиксироваться в форме, пригодной для последующей валидации независимым подразделением:

```
{ идентификатор анализа, версия правил, хеш входного файла, отрасль,
  результаты всех проверок целостности, все агрегаты, значения и статусы
  всех индикаторов, значения четырёх ограничителей, связывающий ограничитель,
  множитель, стоп-факторы, итоговое решение, время расчёта }
```

Версия правил меняется при любом изменении справочников, порогов или формул. Два запуска на одном файле с одной версией правил обязаны давать идентичный результат.

### 11.3 Точки интеграции

| Что | Рекомендация |
|-----|--------------|
| Приём файла | синхронно, ограничение 50 МБ, только `.xlsx` и `.xls` |
| Расчёт | синхронный при объёме до ~10 тыс. операций: на 800 операциях полный конвейер занимает менее секунды |
| Хранение | исходный файл, JSON результата и отчёт хранятся вместе; срок хранения задаёт владелец данных |
| Выдача в конвейер заявок | JSON с решением, лимитом, связывающим ограничителем и перечнем сработавших факторов |
| Ручной разбор | экран доразметки неклассифицированных операций с накоплением размеченной выборки для будущего ML-контура |

### 11.4 Чего в этой спецификации нет и что нужно добавить в контуре банка

- Проверка контрагентов по ЕГРЮЛ, ГИР БО, картотеке арбитражных дел и реестру МСП.
- Определение связанных сторон и внутригрупповых оборотов по совпадению учредителей.
- Сверка карточки с фактическими оборотами по счёту клиента в вашем банке — прямая защита от подделки файла.
- Расчёт PD, LGD и резерва.
- Работа с персональными данными и коммерческой тайной по внутренним регламентам.

## 12. Ограничения и открытые вопросы

| Ограничение | Следствие | Что делать |
|-------------|-----------|------------|
| Модель экспертная, без обучающей выборки дефолтов | разделительная способность не измерена, PD не рассчитывается | ретроспективный прогон на закрытых заявках, расчёт Gini по каждому индикатору |
| Файл формирует клиент | возможна «причёсанная» карточка | контроль целостности V1–V2, в перспективе — сверка с оборотами в своём банке |
| Индикаторы 18-МР используются как кредитные факторы | недопустимо трактовать их как основание для отказа в обслуживании счёта | разделить кредитный и комплаенс-контуры на уровне регламента |
| Детектор транзита даёт ложные срабатывания на дистрибуции с коротким циклом | занижение лимита у здорового клиента | транзит вычитается и флагуется, но до 60 % не приводит к автоотказу |
| Мультивалютные операции не обрабатываются | карточка со счётом 52 отбраковывается с предупреждением | курсовая переоценка в отдельной задаче |
| Отраслевые коэффициенты заданы экспертно | систематическое смещение лимита по отраслям | калибровка по фактической оборачиваемости портфеля |
